1: [Normal] 一、需求背景
2: [Normal] 封装工程师在 Cadence Allegro 中设计新板时，经常需要查找历史上形态相近的封装，以便复用焊盘栈、异形铜箔轮廓和已验证的布局经验。传统做法依赖人工记忆、数据库搜索或模糊匹配，存在效率低、易遗漏、难以快速定位最优参考等痛点。
3: [Normal] 本次开发的封装比对子模块就是基于设计部提供的 Allegro 封装 JSON，将各 Pin 的铜箔形状还原为精确几何，再以几何 IoU 在历史库中检索形态最接近的封装。需要实现以下功能：
4: [List Bullet] 1.接收设计部标准封装 JSON，解析参数化焊盘与异形 Shape 轮廓；
5: [List Bullet] 2.将封装还原、归一化并缓存为 fpgeom 二进制格式，支持 PostgreSQL 历史库入库与去重；
6: [List Bullet] 3.对查询封装与库内候选做 pin 数硬过滤后，全量计算几何 IoU（含 0/90/180/270° 旋转取最优），返回 Top-K 及来源板号；
7: [List Bullet] 4.提供 HTTP REST 接口供 Agent / 上层系统调用，支持「先入库再检索」与多请求并发；
8: [List Bullet] 5.比对结果可解释：返回 iou、best_rotation_deg、source_board 等字段，便于工程师复核。
9: [Normal] 二、需求目标
10: [Normal] 本模块负责“已有 Allegro 封装之间的形态相似检索”。目标是在内网环境下实现可工程化部署、秒级响应、结果可解释的封装比对能力。
11: [List Bullet] 1.当前：JSON → fpgeom → PostgreSQL 入库；pin 硬过滤 + 几何 IoU 精排；FastAPI 接口 + 多进程 IoU 加速；
12: [List Bullet] 2.待做：万级-百万库粗召回；除了pin数外还有什么可作封装匹配的过滤条件加入，加快筛选封装的速度。

15: [Normal] 3.1.1 在线检索主路径

19: [Normal] 3.2 几何 IoU 比对方案
20: [Normal] 核心需求是“封装铜箔形态是否相近”，需要精确比较焊盘排列、异形轮廓与 void 挖空。选用 Shapely 精确多边形计算IoU；对候选封装尝试B相对A的4个90°旋转，取最大IoU。中间格式fpgeom采用msgpack序列化归一化多边形，文件（.fpgeom）与数据库BYTEA同格式，比对时不重复解析JSON。
21: [Normal] 检索策略（yaml文件里面的配置）：
22: [List Bullet] 1.pin_filter=true：仅与 pin_count 相同的库内记录比对；
23: [List Bullet] 2.全量 IoU 精排后，丢弃 iou < min_iou 的结果；
24: [List Bullet] 3.按 IoU 降序取 top_k；排除与查询同名同文件的记录。

48: [Normal] 3.8 部署与服务接口
49: [Normal] 服务层采用 FastAPI + uvicorn（Linux/Windows 均可）；比对为 CPU 密集几何计算，无需 GPU。
50: [List Bullet] 1.GET /health — 健康检查与数据库连通性；
51: [List Bullet] 2.GET /api/v1/footprints/settings — 读取当前 YAML 策略与并发配置；
52: [List Bullet] 3.POST /api/v1/footprints/library — 上传 JSON，解析 fpgeom 并 UPSERT；
53: [List Bullet] 4.POST /api/v1/footprints/similar — 上传查询 JSON，pin 过滤 + IoU Top-K；save_to_library=true 时先入库再检索。
54: [Normal] 3.9 并发与性能
55: [Normal] similar 接口支持多并发：max_concurrent_similar 限制同时检索请求数；共享 ProcessPoolExecutor 执行 IoU。128 核示例：可用 80 核、10 并发、每路约 8 进程。uvicorn_workers 必须保持 1。pin 过滤后候选数百条以内，多进程 IoU 为秒级。

对比项 | PostgreSQL（选用） | 说明
结构化查询 | 支持 | pin_count 硬过滤走 B-tree 索引，SQL WHERE pin_count = ? 毫秒级
二进制大对象 | BYTEA 原生支持 | fpgeom 为 msgpack 二进制，一次读出即可 IoU，无需拆多表
JSON 归档 | JSONB + GIN 可选 | source_json 保留原始 JSON，便于审计、重导、算法升级重算
去重与 UPSERT | 唯一索引 content_hash | 同一 JSON 内容 sha256 去重，支持 insert/update
扩展性 | 千~百万行可扩展 | 当前全量 IoU 精排；二期可加粗召回索引列，无需换库
部署成熟度 | 内网常用、运维熟悉 | 与其它模块统一 PostgreSQL 技术栈
IoU 不入库 | 查询时现场计算 | 相似度随 query 变化，算法迭代无需刷 N² 关系表
