# 场景重估与方案调整

版本 v0.2 ｜ 2026-08-05
> 本文结合实际设计场景的特点（板型跨度大、规范体系成熟、设计数据合规要求高）以及 6 个月 PoC 周期，对前六份文档做重大修正。**若与前文冲突，以本文为准。**

---

## 一、设计场景带来的关键差异

| 场景特点 | 对项目的影响 |
|---|---|
| 历史设计数据量可能远超 500~5000 的保守假设 | **数据量可能不是瓶颈**，需在盘点后核实，这个数字直接决定技术路线的激进程度 |
| 板型跨度极大：从简单工控板到几十层、十万级管脚、112Gbps 的高速板 | 一个模型很难通吃，必须按板型/复杂度分层建模，或者先锁定一个细分场景 |
| 具备 SI/PI/EMC 仿真条件 | **可以给布局方案做真实物理评价，这是 RL 奖励信号的金矿** |
| **已有"成熟细致的设计规范体系"和"模块化的设计分工流程"** | 知识库不是从零梳理，是把成熟体系数字化，**工程量小于预期、质量高于预期** |
| 精细化分工：建库 → 规则设计 → **器件布局** → 规则驱动布线 → 质量评审 → 可制造性检查 → 工程输出 | **流程本身就是天然的数据标注结构和产品切入点** |
| 设计数据有保密约束 | **设计数据合规是头号风险**（见第二节） |

### 1.1 重估结论：有利因素

1. **数据量可能是核心资产而不是瓶颈。** 如果实际有几千到几万块历史板，模仿学习和离线 RL 的数据基础相当扎实，前文中"小样本"的顾虑基本解除。**请务必核实可用于训练的合格板数**，它直接决定技术路线的激进程度。
2. **标注可以分散完成。** pairwise 布局偏好标注不必集中占用少数专家的工时，可以分给多位设计工程师，每人标几十到上百对，短时间内就能凑够几千对。**这个条件要用足。**
3. **规范体系已成熟。** 规范体系的目标就是保证"设计质量不依赖个人经验"，说明规范已经是结构化、可执行、有分级的，知识库项目的起点较高。
4. **有真实物理评价能力。** SI/PI/EMC 仿真能对布局方案给出客观评价，可以用来校准代理评估器、构造奖励模型。

### 1.2 重估结论：不利因素

1. **设计数据合规是可能致命的风险**（详见第二节）。
2. **板型跨度过大**，一个模型很难通吃工控板和 112Gbps 高速板。必须按板型/复杂度分层建模，或者先锁定一个细分场景。
3. **PoC 周期只有 6 个月**，按 `06-路线图与里程碑.md` 的完整形态铺开肯定做不完，必须大幅收缩范围（详见第四节）。
4. **SKILL 开发是小众技能**，`.brd` 提取与写回脚本是关键路径，需要尽早验证（见 4.2）。

## 二、头号风险：设计数据的使用权

**这是全项目最大的风险，而且不是纯技术问题。请在写任何代码之前先确认数据使用边界。**

### 2.1 问题本质

历史设计数据通常带有保密约束：设计成果与过程数据仅用于对应项目，不得用于其他用途。直接用它们训练一个通用的 AI 模型，可能超出约定的使用范围。

**最坏情况**：模型训练好了，因数据授权问题无法使用，项目归零。

### 2.2 必须在第 1 个月内确认的事

| 问题 | 需要的结论 |
|---|---|
| 现有设计数据的使用范围是怎么界定的？ | 逐类梳理，分出"可用"、"需授权"、"绝对不可用"三档 |
| 能否在脱敏后用于内部工具训练？ | 明确口径，最好有书面意见 |
| 是否存在没有保密约束的数据？ | 如内部培训案例、演示板、开源硬件、已过保密期的项目 |
| 模型是否会"记忆"训练数据并泄漏？ | 需要技术方案 + 测试报告支撑判断 |

### 2.3 技术侧的合规设计

| 措施 | 说明 |
|---|---|
| **不存原始设计，只存抽象表示** | 训练用的是图结构 + 统计特征 + 相对布局，不保留可还原的完整设计文件 |
| **强脱敏** | 项目名、敏感名称、器件型号做一致性映射；网络名归一化为类型标签（如 `DDR_DQ_0` → `HS_DATA_x`） |
| **模块级而非整板级** | 只学习"去耦电容怎么放"这类通用工艺知识，不学习具体产品的整体架构。**通用工艺知识属于行业公共知识，合规上更容易站得住** |
| **记忆化测试** | 定期用训练集中的特有信息构造探测问题，验证模型不会吐出原始设计细节，形成测试报告 |
| **来源级隔离开关** | 数据集支持按来源/项目剔除，便于应对个别数据的特殊要求 |
| **差分隐私（可选）** | 训练时加噪，进一步降低记忆风险 |

> **技术定位**：把项目定位为"把**设计工艺方法论**沉淀为工具"，而不是"把某个具体设计整体搬到另一个设计里复用"。前者是通用的 know-how，后者才是雷区。**技术方案要围绕这个定位来设计**（这就是为什么要做模块级、抽象表示、通用工艺规则，而不是整板复用）。

**注意**：这个定位会影响技术方案——它意味着 `04-算法方案` 里的"整板级检索复用"要谨慎（涉及完整产品结构），而"外围小器件摆放"这类通用工艺问题则安全得多。这也进一步支持了第三节的选择。

## 三、算法路线的重大调整：把 RL 的第一个战场选对

你的原话是"能落地最快的为主，但我想做能自动化的、规则性强的、能用 RL 学到规则并排布出来的"。结合场景特点，我认为最优解非常明确：

> ## 首个 RL 攻坚目标：**外围小器件的自动摆放**
> （去耦电容、上下拉电阻、串联匹配电阻、滤波电容、ESD 器件等两端小器件）

### 3.1 为什么是这个场景

| 维度 | 说明 |
|---|---|
| **规则性极强** | 去耦电容离电源引脚多远、放哪一面、过孔怎么打、优先级顺序——规范里写得清清楚楚，**正是你想要的"RL 学规则"的场景** |
| **数据量最大** | 一块板几百到上千个小器件，几千块板就是**百万级样本**，模仿学习绰绰有余 |
| **问题局部化** | 每个小器件只需在关联主芯片周围的局部区域决策，动作空间小，**6 个月内做得完** |
| **评价客观** | 距离、过孔数、是否跨分割、回流路径长度、是否遮挡——全部可自动计算，不依赖主观判断 |
| **合规安全** | 属于通用工艺知识，不涉及具体产品架构，**合规风险最低** |
| **重复劳动多** | 这是纯消耗工时的机械劳动，**自动化收益直接可见** |
| **工程师抵触最小** | 没人喜欢手动摆几百个电容，这不是"AI 抢我的活"，是"AI 帮我干脏活" |
| **是完整链路的最小验证** | 图建模、GNN 编码、动作掩码、RL 训练、合法化、写回——**全套技术栈都跑通了，只是规模小**。成功后向模块级、整板级扩展是自然演进 |

### 3.2 与"整板布局"相比的取舍

| | 外围小器件摆放 | 整板/模块布局 |
|---|---|---|
| 6 个月内做成的概率 | **70%+** | < 20% |
| 数据合规风险 | 低 | 中~高 |
| 技术含量 | GNN+RL 全套，只是规模小 | 同左 |
| 应用价值 | 中（但确定） | 高（但不确定） |
| 对下一阶段的价值 | **完整技术底座 + 已验证的数据管道** | — |

**结论**：先用小器件摆放把 GNN+RL 的完整链路和数据管道跑通并交付价值，第二阶段（V1）再扩展到模块级和整板级。这不是降低目标，是**用正确的顺序达成目标**。

## 四、PoC 范围收缩

### 4.1 收缩后的范围（6 个月能做完的）

| 模块 | 原目标 | **调整后目标** |
|---|---|---|
| 知识库问答 | 完整自研 RAG 平台，300 题评测 ≥ 85% | **基于开源框架（RAGFlow/Dify）快速搭建 + 针对性优化解析与检索，评测 ≥ 80%，Web 端交付** |
| 规则引擎 | 200 条规则，Allegro 插件集成 | **降级为 P2，本期只做规则 DSL 设计 + 30~50 条示范规则，不做完整产品** |
| 辅助布局 | 模块级完整方案 | **收敛到"外围小器件自动摆放"单一场景，做深做透** |
| Allegro 插件 | 完整插件 v2 | **降级为最小可用：命令行/独立客户端 + 文件交换，插件放到 V1** |
| API 服务 | 完整 OpenAPI | 保留（工作量小） |

### 4.2 关键技术缺口（按紧急程度）

1. **数据管道（最紧急）**
   数据管道（`.brd` 批量提取、PDM 转换、图构建）本身就是 2~3 个月的活，如果和算法开发串行做，6 个月肯定做不完。必须从第 1 天就和算法并行推进。
   **关键能力**：懂 Allegro 数据结构、会写提取脚本、懂设计业务（知道哪些字段有意义）。

2. **SKILL 开发**
   建库、批量改属性、出报告这类 SKILL 自动化脚本在设计侧通常已有积累（之前封装形状还原用的 JSON 就是 SKILL 导出的），**优先复用现有脚本和经验**，比从零摸索快得多。

3. **领域专家参与**
   规则确认、标注、评审都离不开资深工程师的判断：
   - 资深工程师深度参与规则确认与评测（全程）
   - pairwise 布局偏好标注分散给多位设计工程师（每人 2~4 小时，集中在 M4~M5）

4. **后端 + 前端（可延后）**
   PoC 阶段用 FastAPI + Streamlit/Gradio 顶一下够用，正式产品化再完善。

### 4.3 按工作流划分

| 工作流 | M1~M3 | M4~M6 |
|---|---|---|
| **数据管道** | `.brd` 提取、PDM、数据清洗 | 数据集维护、特征工程 |
| **图建模 / GNN** | 图构建 + GNN 预训练 | 为小器件摆放提供编码器 |
| **小器件摆放（RL 主线）** | 规则基线 + 环境原型 | BC → RL → 评估 |
| **环境 / 评估 / 可视化** | 评估器原型 | 环境工程、评估器、可视化 |
| **知识库** | 解析、检索、问答、评测集 | 知识库优化 + 上线运营 |
| **规则 DSL** | — | 规则 DSL + 示范规则 |
| **SKILL 脚本** | 提取脚本 | 写回脚本、最小插件 |

## 六、需要尽快确认的三件事

1. **实际可访问、可用于训练的历史设计数据有多少？**（文中保守假设 500~5000，实际量直接决定技术路线可以多激进。）
2. **设计数据能否用于内部 AI 工具训练？使用边界是什么？**（这可能是项目的生死开关，越早确认越好。）
3. **外围小器件在一块板里的数量、以及手工摆放的耗时占比是多少？**（这决定首战场景的价值上限。）
