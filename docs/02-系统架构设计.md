## 1. 架构总览

系统分为 6 层，从下往上：

```
┌───────────────────────────────────────────────────────────────────────────┐
│ L6 接入层  Allegro 插件(SKILL) │ Web 控制台 │ REST/gRPC API │ CI 流水线钩子 │
├───────────────────────────────────────────────────────────────────────────┤
│ L5 智能应用层                                                              │
│   规范问答 Agent │ 符合性检查服务 │ 布局建议服务 │ 相似设计检索 │ 报告生成    │
├───────────────────────────────────────────────────────────────────────────┤
│ L4 能力层                                                                  │
│   RAG 引擎 │ 规则引擎 │ 布局推理引擎(GNN+RL) │ 布局评估器 │ LLM 推理服务     │
├───────────────────────────────────────────────────────────────────────────┤
│ L3 数据资产层                                                              │
│   向量库 │ 全文索引 │ 规则库 │ 图数据库 │ 设计元数据库 │ 特征库 │ 对象存储    │
├───────────────────────────────────────────────────────────────────────────┤
│ L2 数据处理层                                                              │
│   文档解析/OCR │ 分块与打标 │ 向量化 │ 设计图构建 │ 特征工程 │ 数据脱敏      │
├───────────────────────────────────────────────────────────────────────────┤
│ L1 数据接入层                                                              │
│   Allegro Extracta │ SKILL 导出 │ IPC-2581 解析 │ CM 约束导出 │ 文档采集     │
├───────────────────────────────────────────────────────────────────────────┤
│ L0 基础设施  K8s / Docker │ GPU 调度 │ 对象存储 │ 监控告警 │ SSO/权限        │
└───────────────────────────────────────────────────────────────────────────┘
```

## 2. 分层详细设计

### 2.1 L1 数据接入层

**目标**：把 EDA 私有格式和散落文档，变成平台可消费的结构化数据。这是整个项目的**生死线**，第一个月必须打通。

#### 2.1.1 设计数据接入（三条路径，互为备份）

| 路径 | 方式 | 优点 | 缺点 | 定位 |
|---|---|---|---|---|
| **A. Allegro Extracta** | 调用 `extracta.exe` + 视图文件（`.txt` view file），导出器件、引脚、网络、坐标、层、Room 等表格 | 官方工具、批量、纯文本、无需打开 GUI | 字段需按视图定义、部分高级信息缺失 | **批量历史数据提取主力** |
| **B. SKILL 脚本** | Allegro 内置 Lisp，可读写板数据库 | 能拿到几乎全部信息、可写回坐标 | 需 Allegro 进程、批处理需 `allegro -s` 无界面模式 | **插件交互 + 写回主力** |
| **C. IPC-2581 / ODB++** | 从 Allegro 导出中立格式，用开源库解析 | 跨 EDA、标准化、易解析 | 导出需人工/脚本触发，约束信息可能损失 | **兜底与跨工具扩展** |

**约束数据**：Constraint Manager 支持导出（CSV / 电子表格 / XML），单独走一条管道，与规则库做对齐校验。

**架构原则**：定义统一的中间表示 **PDM（PCB Design Model）**，所有路径最终归一到同一套 Schema。上层不感知数据来自哪条路径。

```
Allegro .brd ──┬─→ Extracta ────┐
               ├─→ SKILL 导出 ──┼─→ 归一化适配器 ─→ PDM (JSON/Parquet) ─→ 上层
               └─→ IPC-2581 ────┘
```

**PDM 核心实体**：
- `Board`：板框轮廓、叠层、层定义、单位、原点
- `Component`：refdes、器件型号、封装、尺寸包围盒、高度、面（Top/Bottom）、坐标、旋转、是否固定、所属 Room、功率
- `Pin`：所属器件、引脚号、坐标、所属 Net、焊盘类型
- `Net`：名称、引脚列表、Net 类型（电源/地/高速/模拟/时钟）、约束引用
- `Constraint`：物理/间距/电气约束集及其绑定对象
- `Region`：Room、Keepout、限高区、禁布区
- `Via` / `Trace`（布线后才有，PoC 阶段用于评估）

#### 2.1.2 文档接入

- 文件服务器 / SharePoint / PLM 定时扫描 + 手动上传双通道
- 记录文档指纹（哈希）、版本、密级、责任人、生效日期
- 变更监听：文档更新自动触发重新解析与索引

### 2.2 L2 数据处理层

#### 2.2.1 文档处理流水线

```
原始文档 → 格式识别 → 版式解析(含OCR/表格/公式) → 结构化中间表示(带标题树)
   → 语义分块 → L1/L2/L3 分类打标 → 元数据富化 → 向量化 → 入库(向量+全文+图)
```

关键点：
- **表格必须单独处理**。规范里的数值绝大多数在表格中。表格转成结构化 JSON 并保留原始渲染图，检索时整表召回，避免行列错位导致数值张冠李戴。
- **图片处理**：规范中的"正确/错误示例图"用多模态模型生成描述文本参与检索，原图在答案中展示。
- **分块策略**：以标题层级为主边界，块大小 300~800 token，块间重叠 15%，每块携带完整的标题路径（如 `高速设计规范 > 4. DDR 设计 > 4.2 等长要求`）作为上下文前缀。
- **L1/L2/L3 打标**：LLM 初分 + 专家复核，结果写入块的元数据。L1 块额外进入规则抽取队列。

#### 2.2.2 设计数据处理流水线

```
PDM → 数据校验 → 脱敏(项目名/敏感名称/涉密网络名映射) → 设计质量分级
   → 异构图构建 → 节点/边特征工程 → 图数据集(训练用) + 图索引(检索用)
```

**脱敏**：训练数据中的项目名、敏感名称、涉密器件型号做一致性映射（同一实体映射到同一代号，保持图结构不变）。映射表单独加密存储。

**设计质量分级**：只有"已量产 + 无重大质量问题 + 资深工程师认可"的板才能进 RL 训练集的"专家轨迹"。分级由 SME 打标 + 自动指标（DRC 干净度、改版次数）联合判定。

### 2.3 L3 数据资产层

| 存储 | 选型建议 | 存放内容 |
|---|---|---|
| 向量数据库 | **Milvus**（大规模）或 **Qdrant**（轻量易运维） | 规范文本块向量、设计模块图向量 |
| 全文检索 | **OpenSearch / Elasticsearch** | 规范文本、BM25 关键词检索 |
| 关系数据库 | **PostgreSQL** | 文档元数据、规则库、用户、权限、审计、检查报告 |
| 图数据库 | **Neo4j** 或 **PostgreSQL + AGE** | 规范知识图谱、设计网表图（用于子图匹配检索） |
| 对象存储 | **MinIO** | 原始文档、`.brd` 归档、模型权重、布局截图 |
| 特征/数据集 | **Parquet on MinIO + DVC/LakeFS** | 图数据集、训练样本，含版本管理 |
| 缓存 | **Redis** | 会话、检索缓存、任务队列 |

### 2.4 L4 能力层（核心）

#### 2.4.1 RAG 引擎

```
用户问题
  ├─→ 查询理解：术语归一化、缩写扩展、意图分类(规范查询/原理解释/案例检索/设计检查)
  ├─→ 查询改写：多路 Query 生成（HyDE / 子问题分解）
  ├─→ 混合召回：向量 Top-K(50) ∪ BM25 Top-K(50) ∪ 图谱关联条款
  ├─→ 重排（Reranker）：Cross-encoder 精排取 Top-8
  ├─→ 上下文组装：补齐父章节、关联表格、图片
  ├─→ 生成：LLM 生成答案，强制引用标注
  └─→ 后校验：引用有效性检查、数值一致性检查、无依据则拒答
```

**必须做的三件事**：
1. **强制引用**：答案中每个论断都要能追到具体文档、章节、页码。工程师不信任无出处的答案。
2. **数值二次校验**：答案中的数值必须在召回的上下文中原样出现，否则触发告警或降级为"请查阅原文"。
3. **意图路由**：如果用户问的是"我这块板符不符合规范"，应路由到规则引擎而不是 RAG。

#### 2.4.2 规则引擎

```
规则来源
  ├─ LLM 从 L1 规范块抽取候选规则 → 人工确认 → 规则库
  ├─ 从 Constraint Manager 导出反向生成
  └─ 工程师手工编写
        ↓
    规则 DSL（YAML + 表达式）
        ↓
   规则编译器 → 可执行检查算子
        ↓
   执行引擎（对 PDM 数据执行）→ 违反项 → 报告 / Allegro 高亮
```

**规则 DSL 示例**（说明性草案）：

```yaml
rule_id: PL-DECAP-001
name: BGA 去耦电容距离要求
source: {doc: "布局设计规范 v3.2", section: "5.3.2", page: 41}
category: L1_hard
severity: major
scope:
  target: Component
  filter: "component.type == 'CAP' and component.value in ['0.1uF','100nF']"
condition: |
  for each pin P in nearest_power_pins(component, k=1):
    distance(component.center, P.location) <= 5.0mm
    and same_side_or_opposite_direct(component, P.owner)
message: "去耦电容 {component.refdes} 距电源引脚 {distance}mm，超出规范要求 5mm"
fix_hint: "将该电容移至芯片电源引脚 5mm 范围内，优先放置于芯片背面对应位置"
applies_to:
  board_type: ["digital", "mixed"]
  speed_class: [">=1Gbps"]
```

**设计要点**：
- 规则必须携带 `source`（可溯源到规范原文），检查报告里直接展示，这样工程师才服气。
- 规则有 `applies_to` 适用范围，因为板类型多样，不同板类规则不同。
- 规则同时输出 `severity` 和 `fix_hint`，后者可作为布局引擎的修复动作。
- **规则引擎与布局引擎共享同一套规则**：规则引擎用于"事后检查"，布局引擎用于"事中约束"（动作掩码 + 奖励惩罚）。这是架构上的重要复用。

#### 2.4.3 布局推理引擎

详见 `04-算法方案-GNN与RL结合的辅助布局.md`。架构上分为四个可独立部署的服务：

| 服务 | 职责 |
|---|---|
| **图编码服务** | 异构 GNN 编码器，输出器件/网络/子图的嵌入表示 |
| **检索复用服务** | 基于图嵌入 + 子图匹配，召回历史相似模块及其布局 |
| **策略服务** | RL 策略网络，序列化决策器件位置；带动作掩码 |
| **优化与合法化服务** | 解析式/力导向精细优化 + 重叠消除 + 网格对齐 + 硬约束修复 |

**推理链路**：
```
PDM + 结构约束
  → 图构建 → 图编码
  → [路径 A] 相似模块检索 → 模板套用（快，工程师最认可）
  → [路径 B] RL 策略逐步摆放（覆盖无模板的部分）
  → 融合 → 解析式精细优化 → 合法化 → 评估打分
  → 生成 3~5 个候选方案 + 解释 → 返回插件
```

#### 2.4.4 LLM 推理服务

- 统一网关，屏蔽底层模型差异，支持模型热切换与灰度
- 多模型：主对话模型（大）、抽取/分类模型（小，高吞吐）、Embedding、Reranker、多模态
- 推理框架：vLLM / SGLang，支持并发与批处理
- 显存与 GPU 调度：推理与训练物理隔离，避免训练把推理挤爆

### 2.5 L5 智能应用层

**Agent 编排**：以"规范问答 Agent"为主入口，能调用工具（Tool Calling）：

| 工具 | 用途 |
|---|---|
| `search_spec(query)` | 检索设计规范 |
| `check_design(board_id, rule_set)` | 触发规则检查 |
| `find_similar_designs(module_graph)` | 相似设计检索 |
| `suggest_placement(scope, constraints)` | 请求布局建议 |
| `query_design_data(board_id, sql_like)` | 查询当前设计的具体数据（如"这块板有几个 BGA"） |
| `get_component_info(part_number)` | 器件库查询 |

这样工程师一个入口即可完成"问规范 → 查我的板 → 检查 → 要建议"的完整链路。

### 2.6 L6 接入层

#### 2.6.1 Allegro 插件（SKILL）

```
Allegro (SKILL)
  ├─ 自定义菜单 / 工具栏 / 侧边面板
  ├─ 采集当前设计上下文（选中器件、当前 Room、板级信息）
  ├─ HTTP 客户端 → 平台 API（SKILL 可通过 ipcBeginProcess / 外部进程桥接）
  ├─ 结果渲染：违反项列表、建议位置（以临时图形/Room 高亮方式预览）
  └─ 写回：确认后调用 SKILL API 修改器件坐标（支持 undo）
```

> **架构风险点**：SKILL 的网络能力有限，通常需要一个**本地代理进程（Local Agent）**。建议架构为：
> `Allegro SKILL ↔ 本地代理（Python/C++，跑在工程师机器上）↔ 平台服务（内网服务器）`
> 本地代理负责 HTTP 通信、大文件传输、结果缓存，SKILL 只负责 UI 与板数据读写。这个设计还能顺带解决插件升级问题。

#### 2.6.2 Web 控制台

规范问答界面、知识库管理、规则库编辑与版本管理、检查报告中心、布局方案查看器（2D 渲染）、模型与数据集管理、评测看板。

#### 2.6.3 API

REST（OpenAPI 3.0）为主，长耗时任务（布局推理）走异步任务 + 回调/轮询。gRPC 供内部服务间高性能调用。

## 3. 关键架构决策记录（ADR）

| 编号 | 决策 | 理由 | 备选方案 |
|---|---|---|---|
| ADR-01 | 引入统一中间表示 PDM | 解耦 EDA 工具与上层算法，未来换 EDA 或多 EDA 并存不用重写算法 | 直接用 Allegro 数据结构（被否：绑死） |
| ADR-02 | 规则引擎与布局引擎共享规则库 | 保证"检查标准"与"生成标准"一致，避免 AI 生成的布局通不过自己的检查 | 各自维护（被否：必然漂移） |
| ADR-03 | 布局采用"检索复用 + 模仿学习 + RL 微调"三段式 | 500~5000 个历史板是宝贵的专家轨迹，纯 RL 从零探索在 6 个月内几乎不可能出成果 | 纯 RL（被否：风险过高） |
| ADR-04 | 硬约束通过动作掩码 + 合法化后处理保证，而非仅靠奖励惩罚 | 奖励惩罚只能"倾向于"不违反，工程师要的是"绝对不违反" | 仅靠 reward shaping（被否） |
| ADR-05 | Allegro 集成采用"SKILL + 本地代理"双进程架构 | SKILL 网络与并发能力弱，且便于插件热更新 | SKILL 直连服务（被否：能力受限） |
| ADR-06 | 检索采用向量 + BM25 混合 + Reranker | 规范中大量精确术语、型号、条款号，纯向量检索召回差 | 纯向量（被否） |
| ADR-07 | 先落地知识库，再规则引擎，最后布局 | 三者存在数据与认知依赖：规则来自规范，布局评价来自规则 | 并行推进（被否：SME 资源不够，且会重复返工） |
| ADR-08 | 训练与推理 GPU 资源物理隔离 | 布局模型训练是长时间大显存任务，不能影响日常问答服务 | 混布（被否） |

## 4. 部署架构（内网私有化）

```
                    ┌──────────── 内网 ────────────┐
工程师工作站                     应用服务器集群 (K8s)
┌──────────────┐          ┌─────────────────────────────┐
│ Allegro      │          │ API 网关 / SSO               │
│  + SKILL插件 │◄────────►│ RAG服务 │ 规则服务 │ 布局服务  │
│  + 本地代理  │   HTTPS  │ Web 前端 │ 任务队列          │
└──────────────┘          └─────────────────────────────┘
                                      │
                          ┌───────────┴────────────┐
                          │  GPU 推理节点（vLLM）    │
                          │  LLM / Embedding /      │
                          │  Reranker / GNN 推理    │
                          └───────────┬────────────┘
                                      │
                          ┌───────────┴────────────┐
                          │ 存储层                  │
                          │ PostgreSQL │ Milvus     │
                          │ OpenSearch │ Neo4j      │
                          │ MinIO │ Redis           │
                          └────────────────────────┘

                          ┌────────────────────────┐
                          │ 训练集群（物理隔离）      │
                          │ A100/H100 多卡          │
                          │ Ray + PyTorch + PyG     │
                          │ MLflow 实验管理          │
                          └────────────────────────┘
```

**GPU 资源规划建议（PoC 阶段）**：
- 推理：2 卡（1 张跑主 LLM，1 张跑 Embedding + Reranker + GNN 推理）
- 训练：4~8 卡（GNN 预训练、模仿学习、RL 训练；RL 需要大量并行环境采样，CPU 核数也要跟上，建议 ≥ 64 核）
- 布局仿真环境（HPWL / 拥塞估计）建议 GPU 加速实现，否则 RL 采样会成为瓶颈

## 5. 安全与合规

| 措施 | 说明 |
|---|---|
| 网络隔离 | 全系统部署于内网，无出口；模型与依赖通过离线仓库分发 |
| 数据分级 | 文档与设计按密级打标，检索与问答强制按用户权限过滤（在检索阶段过滤，而非生成后过滤） |
| 训练数据脱敏 | 项目名/敏感名称/涉密型号一致性映射，映射表加密单独存储 |
| 传输加密 | 全链路 HTTPS / mTLS |
| 审计 | 所有问答、检查、布局请求与结果留存，含用户、时间、板号 |
| 模型保护 | 模型权重加密存储，服务化调用，不下发到工作站 |
| 越权防护 | 检索层强制注入权限过滤条件，防止通过提问套取无权限文档内容 |

## 6. 演进路线（架构视角）

| 阶段 | 架构重心 |
|---|---|
| PoC（0~6 月） | 单集群、单租户、能力打通优先；布局引擎以模块级、离线批处理为主 |
| V1（6~12 月） | 多项目隔离、实时交互式布局、Allegro 深度集成、规则库规模化 |
| V2（12~24 月） | 布局-布线联合优化、SI/PI 仿真闭环、跨 EDA 支持、主动式设计助手（在工程师操作时实时提示） |
