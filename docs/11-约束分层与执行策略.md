# 约束分层与执行策略：知识库、规则 DSL 与代码各管什么

版本 v0.1 ｜ 2026-09-09
> 回答的问题：**做 RL 布局时，规范里那些"硬的"、"软的"、"模糊的"东西，哪些做成知识库、哪些用代码强制、哪些交给学习？**
> 结论先行：对 RL 来说"知识库 vs 代码"是假二选一。策略网络只看得见数字，任何要影响策略的约束最终必然落成代码或参数；知识库的角色是**规则的上游、规则集的选择器、输出的解释、奖励设计的参考**，而不是运行时的约束来源。
> 配套代码：`layout_rules/`（可运行的最小实现，见第七节）。

---

## 一、为什么不能二选一

| 方案 | 问题 |
|---|---|
| 全部进知识库，让 LLM 在决策环里读 | 秒级延迟、不确定、不可复现；`docs/08` 的环境目标是 ≥1000 步/秒、百万次交互。NeurPCB 的 Deep Review 就是这条路，它没有训练能力 |
| 全部写死在代码里 | 板型多样，同一条"去耦电容距引脚 ≤ 5mm"在工控板和 112Gbps 板上数值不同、不同项目的规范也不同；`NeurPCB/src/routing/critic.py` 把 0.5mm / 0.2mm / 15mm / 90% 全写成字面量，是反例 |
| 硬约束靠奖励惩罚 | 只能"倾向于不违反"。MaskPlace 的对照实验：把重叠从硬掩码放松成软约束后 HPWL 变好但重叠率不再为零；PCBWorld 把 DRV 放进惩罚，但仍用 action mask 过滤不可执行动作，且主指标 Clean Pass 要求 DRV=0（`docs/02` ADR-04） |
| 软约束做成掩码 | 可行集被砍空。Component-Centric Placement（arXiv 2602.23540）把"必须靠近所连网络"当硬约束时奖励极稀疏学不动，改成 Top-K 松弛才能训练 |

## 二、四层模型

```
┌──────────────────────────────────────────────────────────────────────────────┐
│ L-K 知识库层（规范原文 / 评审记录 / 失效分析）                               │
│   服务对象：人、LLM 问答、规则抽取、输出解释。RL 不直接消费。                 │
├──────────────────────────────────────────────────────────────────────────────┤
│ L-R 结构化规则层（YAML DSL：对象 / 检查器 / 阈值 / severity / applies_to / source）│
│   知识库与代码之间唯一的“翻译层”，也是唯一需要专家逐条确认的地方。           │
├──────────────────────────────────────────────────────────────────────────────┤
│ L-C 代码执行层：同一条 DSL 按 enforcement 编译为                               │
│   mask（动作掩码） / penalty（每步惩罚） / terminal_penalty（终局惩罚） / eval_only │
│   代码只写“机制”，阈值全部来自 DSL / Allegro 导出 / 历史数据 / SI 校准。       │
├──────────────────────────────────────────────────────────────────────────────┤
│ L-L 学习层（BC + Critic_expert 偏好判别器）                                   │
│   写不出条文的审美与风格。任何试图写成规则的版本都会得到一堆误报。           │
└──────────────────────────────────────────────────────────────────────────────┘
```

与既有文档的关系：`docs/00` 的 L1/L2/L3 分类是输入；`docs/05` §2.4 的"L1→DSL、L2→评分项、L3→RAG"是流水线；本文补上两点——**同一条规则如何按 severity 切换 mask/penalty**，以及**哪些东西根本不该写成规则**。

## 三、判定一条约束该放哪：五个问题

不要靠"感觉它硬不硬"分类，按下面顺序过：

```
Q1 能形式化吗？（有判定对象、能从 PDM 算出的量、有阈值或能定阈值）
   否 → kind=knowledge（进 RAG）或 kind=preference（交给学习）
   是 ↓
Q2 违反一次工程师就不再信任了吗？
   是 → enforcement=mask（tier=must）
   否 ↓
Q3 放下这一颗器件就能判定，还是整组器件的集合属性？
   集合属性（均匀性、频段搭配、平面被打成筛子）→ scope=layout, enforcement=terminal_penalty
   单步可判 ↓
Q4 阈值随板类 / 项目 / 工艺变化吗？
   变 → kind=parametric_hard，阈值进 DSL params + applies_to；代码里不许出现字面量
   不变 → kind=invariant
Q5 有可靠的自动代理量吗？
   有 → 可进训练信号（mask / penalty）
   需校准（如环路电感）→ needs_calibration=true，校准前只作 eval_only，不作主奖励
```

**"模糊"要拆成三种**，处理方式不同：

- 阈值没定但方向明确（"尽量近"、"尽量短"）：本质是连续目标 → `kind=soft` 奖励项；或者从 A 级历史板挖分位数（如 95% 分位距离）得到一个数据驱动的软阈值（`threshold_source=data_mined`）。
- 依赖上下文判断（"高速区域附近避免放大电解电容"）：前提条件由 `docs/04` §2.3 的网表语义解析器判定，再套 DSL 的过滤条件；语义判定不可靠时只能降级为 warning/penalty，不能做掩码。
- 纯审美（成行成列、朝向一致、"像老工程师摆的"）：`kind=preference, enforcement=learned`。

## 五、规则 DSL 字段

在 `docs/02` §2.4.2 草案基础上新增 `kind`、`enforcement`、`tier`、`threshold_source`、`needs_calibration`、`tests`：

```yaml
- id: PDN-DIST-001
  name: 小容值去耦电容到电源引脚距离上限
  kind: parametric_hard          # invariant | parametric_hard | soft | preference | knowledge
  enforcement: mask              # mask | penalty | terminal_penalty | eval_only | learned | none
  tier: should                   # must：一定过滤；should：过滤后候选为空则降级为惩罚
  severity: warning              # error | warning | info（事后检查报告用）
  scope: placement               # placement：单步可判；layout：整组集合属性
  check: max_dist_to_pin         # 检查器名（布尔判定）；软指标用 metric 字段
  params: {max_mm: 5.0, value_uF_max: 0.1}
  threshold_source: spec_doc     # geometry | allegro_cm | allegro_dfa | spec_doc | data_mined | si_calibration | expert
  needs_calibration: false
  source: {doc: "布局设计规范 v3.2", section: "5.3.2", page: 41}
  applies_to: {board_type: [digital, mixed], speed_class: ["*"]}
  message: "去耦电容距电源引脚超出 5mm"
  fix_hint: "移至芯片电源引脚 5mm 范围内，优先背面对应位置"
  tests:                         # 正 / 负例夹具，selfcheck 按执行结果判定（Rule2DRC 式）
    - {fixture: dist_pos, expect: pass}
    - {fixture: dist_neg, expect: fail}
```

软规则用 `metric` + `shape` + `weight`：

```yaml
- id: SOFT-DIST-001
  kind: soft
  enforcement: penalty
  metric: dist_to_pin_mm
  shape: {type: hinge, knee: 2.0, normalize: 10.0}   # linear | hinge | quadratic | inverse
  weight: 1.0
```

`schema.py` 里用 `ALLOWED_ENFORCEMENT` 表强制 kind 与 enforcement 的搭配合法（例如 soft 不能做 mask、knowledge 只能 none、warning 级不能做 must 掩码），加载时不合法直接拒绝，防止带病规则进训练环境。

## 六、三种执行形态与分级掩码

```
                        ┌────────────┐
   YAML 规则集 ────────▶│ compiler   │
                        └─────┬──────┘
        ┌─────────────────────┼──────────────────────┐
        ▼                     ▼                      ▼
   mask(candidates)     step_penalty(cand)     evaluate(placements)
   terminal_penalty(placements)
   ── 事中：RL 环境 ──────────────────────      ── 事后：规则引擎 / 评测 ──
```

**分级掩码降级**（`compiler.mask`）：先跑 must 级；再跑 should 级；若 should 把候选集砍空，则回退到 must 结果，并把 should 规则的 id 放进 `MaskResult.degraded`，`step_penalty(..., degraded)` 会把这些规则临时当作惩罚项计算。输出里可以明确标注"该电容未能满足 should 级规则 X"。演示里 `PDN-SIDE-001`（优先背面）就是靠这个机制在背面放满后自然溢到正面。

**一致性**：掩码、惩罚、事后检查三者都从同一份 `BoundRule` 列表派生，不存在"掩码里有、评估器里没有"的漂移（`docs/02` ADR-02）。

## 七、代码：`layout_rules/`

| 文件 | 职责 |
|---|---|
| `model.py` | 最小 PDM：`Board`（板框 / keepout / 限高 / room / 走线通道）、`Component`、`Pin`、`Via`、`Candidate`、`PlacementContext`（带 STRtree 空间索引与按网 numpy 最近邻缓存）、`DfaSpacingTable` |
| `schema.py` | 规则 DSL dataclass + 合法性校验（kind × enforcement 搭配表） |
| `loader.py` | YAML 加载、strict 校验、`select_rules()` 按 `applies_to` 筛选 |
| `checks.py` | 15 个 placement 级 + 2 个 layout 级检查器（布尔判定，返回违反量与说明） |
| `metrics.py` | 6 个 placement 级 + 3 个 layout 级软指标（连续值） |
| `compiler.py` | `compile_ruleset()` → `mask / step_penalty / terminal_penalty / evaluate`，含分级降级 |
| `rules/decap_v0.yaml` | 上面的 30 条规则 |
| `selfcheck.py` | 规则文件校验 + 注册表解析 + 14 个正负例夹具 + 指标可算性 |
| `demo_decap.py` | 合成 15×15 BGA 场景，候选生成 → 掩码 → 惩罚打分 → 贪心 → 终局评估（即 `docs/08` §6 的 B2 基线骨架） |

运行（仓库根目录）：

```
python -m layout_rules.selfcheck
python -m layout_rules.demo_decap --json out.json
```

演示当前结果（14 颗电容、每颗 3522 个候选）：硬约束违反 = 0；should 级掩码把 0.1uF 电容的候选从 ~3300 压到 ~100（全部落在 BGA 背面）；1uF/10uF 因 `PDN-SIDE-001` 不适用、候选保持 ~3100；事后报告只剩 warning/info（DFA 推荐间距、过孔密度、朝向），且每条带出处或标注"（无出处）"提醒补规范章节。

换成 RL 时只需把 `place_greedy` 里"选惩罚最小的候选"替换成"策略网络在 `MaskResult.legal_indices` 上采样"，环境接口不变。

## 八、已知局限与下一步

1. **性能**：当前 shapely 逐对象计算，约 1ms/候选，14 颗电容 ~30s。RL 环境要求 ≥1000 步/秒，下一步必须把 must 级几何掩码改成栅格化 + 形态学膨胀（`docs/04` §6.1），或用 shapely 2 的向量化数组接口一次处理全部候选；当前实现保留为"正确性参考实现"，用来校验向量化版本。
2. **表达式 DSL**：现在的 `check` 是注册表里的检查器名 + 参数，还不是 `docs/02` 里那种自由表达式。这是刻意的：注册表可穷举、可测、不用安全沙箱。等规则超过 50 条、组合需求明显时再引入受限表达式求值。
3. **DFA 方向性**：真实 DFA 表区分 side-to-side / end-to-end 四种关系，现在用整体外形距离；导入 Constraint Manager CSV 后补。
4. **阈值来源接线**：`threshold_source` 现在只是声明；`allegro_cm / allegro_dfa` 的自动导入、`data_mined` 的分位数挖掘脚本都未实现，依赖 D2（`.brd` 提取管道）跑通。
5. **过孔是动作的一部分**：演示中暴露了一个真实问题——后放电容新打的过孔会压到先放电容的焊盘。现在用"新过孔避让已放器件"的启发式兜住；正式方案里过孔位置应进入动作空间或作为合法化后处理，并对应新增一条 `GEO-VIA-002`（新增过孔与器件间距）。
6. **校准**：`SOFT-LOOP-001` 的系数是占位；`docs/10` §2.2 的三层校准链（解析公式 → Z 矩阵 + scikit-rf → SI 仿真）跑通前，它只能 eval_only。
7. **规则版本与冲突**：多份规范对同一对象给不同阈值时需要优先级语义（KiCad 自定义规则"后定义优先"、Allegro 区域覆盖默认值都是可参考的做法），`RuleSource.version` 字段已留位，冲突检测未做。
8. **网表语义解析器**：`value_uF / net_pwr / net_gnd / dfa_class` 现在是手填属性，正式管道由 `docs/04` §2.3 的解析器自动打标。

## 九、给资深工程师的确认清单

- 第四节 30 条中"出处待填"的规则，补规范文档、章节、页码、版本。
- 每条 `parametric_hard` 规则的 severity：哪些是一票否决（error → must 掩码），哪些是应尽量满足（warning → should 掩码或惩罚）。
- `PDN-VIADEN-001` 的过孔密度上限、`SOFT-LOOP-001` 的电感系数：向 SI 工程师要。
- 是否还有首战范围内、本清单没覆盖的硬规则（例如与晶振 / 高速差分线的隔离距离）。
- `GEO-ORIENT-001`（朝向）和 `PREF-ALIGN-001`（对齐）的边界：哪些是规范明写的，哪些只是习惯。
