# 数据工程与评测体系

版本 v0.1 ｜ 2026-08-05

> 一句话结论：**这个项目 70% 的工作量在数据，30% 在模型。数据工程做不好，后面全部白搭。**
>
> ⚠️ **两处重要修正**（详见 [`07`](07-场景重估与方案调整.md)）：
> 1. **数据量以实际盘点为准**：文中 500~5000 是保守假设，实际历史设计量可能更大，需在盘点后修正，并以"可用于训练的合格板数"为准。
> 2. **新增设计数据合规环节**：设计数据使用前必须完成授权确认与数据分级，这是数据工程的第一道关口，不是可选项。

## 二、规范文档数据工程

### 2.1 处理流水线

```
采集 → 去重（哈希） → 版本识别 → 格式转换 → 版式解析 → 质量检查
  → 分块 → L1/L2/L3 分类 → 元数据富化 → 向量化 → 入库
```

### 2.2 元数据 Schema

```yaml
document:
  doc_id: string
  title: string
  version: string            # v3.2
  effective_date: date       # 生效日期
  deprecated: bool           # 是否已废止
  superseded_by: doc_id      # 被哪个版本取代
  owner: string              # 责任人/责任部门
  security_level: enum       # 公开/内部/秘密/机密
  applicable_scope:          # 适用范围（板类型多样，这个很重要）
    board_types: [digital, analog, RF, power, high_speed, flex]
    product_lines: []
  source_path: string
  hash: string

chunk:
  chunk_id: string
  doc_id: string
  heading_path: [string]     # ["高速设计规范","4 DDR设计","4.2 等长要求"]
  page: int
  content: string
  content_type: enum         # text/table/figure/formula
  rule_class: enum           # L1_hard / L2_soft / L3_knowledge
  extracted_rules: [rule_id] # 若为 L1，关联的规则
  entities:                  # 抽取的领域实体
    components: []
    nets: []
    parameters: [{name, value, unit}]
  figures: [image_id]
  embedding: vector
```

### 2.3 表格处理专项（最容易出错，单独立项）

规范中的数值 80% 在表格里，且表格常有合并单元格、跨页、多级表头。

```
PDF 表格 → 结构识别（PP-Structure / MinerU）
        → 转成 Markdown + JSON 双份
        → 多模态模型对照原图二次校验（关键步骤）
        → 数值型条目单独抽取为结构化记录
        → 人工抽检（至少 20%）
        → 入库时整表作为一个 chunk，避免行列拆散
```

**检索时的处理**：表格 chunk 需要在向量化前生成"表格摘要文本"（如"本表规定了不同速率下 DDR 信号的等长偏差要求，涵盖 DDR3/DDR4/LPDDR4"），否则纯表格内容的向量表示很差。

### 2.4 L1/L2/L3 分类与规则抽取

```
规范 chunk
   ↓ LLM 分类（few-shot prompt + 结构化输出）
L1 硬规则 ──→ LLM 规则抽取 ──→ 候选规则 DSL ──→ 专家确认 ──→ 规则库
                                            └──→ 每条规则配单元测试用例
L2 软规则 ──→ LLM 抽取"倾向描述" ──→ 专家确认 ──→ 布局评分函数项 + 权重初值
L3 知识  ──→ 直接入 RAG 知识库
```

**规则单元测试**：每条规则上线前必须配一个"正例设计片段"和一个"负例设计片段"，跑一遍验证规则实现正确。这套测试集也是回归测试的基础。**这一步很多团队会省掉，然后规则库越来越不可信。**

## 三、设计数据工程（布局模型的粮食）

### 3.1 提取流水线

```
历史 .brd 文件仓库
   ↓ 批量调度（每块板一个任务）
Allegro Extracta / SKILL 批处理（无界面模式）
   ↓
原始导出文本 → 解析器 → PDM（统一中间表示，JSON/Parquet）
   ↓
数据校验（字段完整性、坐标合理性、网表连通性）
   ↓
脱敏（项目名/敏感名称/涉密型号一致性映射）
   ↓
网表语义解析（识别器件角色、功能模块、电源域）
   ↓
异构图构建 + 特征工程
   ↓
设计质量分级打标
   ↓
数据集版本化入库（Parquet + DVC）
```

### 3.2 设计质量分级（决定哪些板能进训练集）

| 等级 | 判定标准 | 用途 |
|---|---|---|
| **A（金标准）** | 已量产 + 无重大质量问题 + 改版次数少 + 资深工程师认可 | 模仿学习专家轨迹、评测基准 |
| **B（可用）** | 已量产 + 无重大问题 | RL 训练、预训练 |
| **C（仅结构）** | 完成设计但未量产，或有已知问题 | 仅用于 GNN 自监督预训练（学结构，不学布局） |
| **D（排除）** | 数据不完整 / 实验板 / 有严重质量事故 | 不使用（D 类中的失效案例可单独作为负样本） |

**打标方法**：自动指标（改版次数、DRC 数、是否量产）初筛 + SME 抽样确认。预期 A 类占比 10~20%，即 50~1000 块板，**这个量对模仿学习是够的**。

### 3.3 模块库建设（检索复用的基础）

```
每块历史板 → 模块划分（层次结构 / Room / 图聚类 / 语义规则）
   ↓
每个模块：子图 + 相对布局 + 元数据（主器件型号、功能类型、器件数、面积）
   ↓
GNN 编码 → 模块向量
   ↓
入模块库（向量库 + 图数据库 + 布局快照图片）
```

预估：5000 块板 × 平均 8 个模块 = **4 万个模块**，是一个相当可观的可复用资产库。**这个模块库本身就是一个独立的技术交付物，即使 AI 模型全部失败，它也有用。**

### 3.4 数据增强

针对小样本问题：
- **几何变换**：整板镜像、旋转（注意：需同步变换所有约束，且要检查是否破坏结构约束）
- **器件替换**：同封装同功能的器件互换（如不同厂家的 0.1uF 电容）
- **模块重组**：把不同板的模块组合成合成设计（用于预训练，不用于 BC）
- **扰动**：对历史布局做小幅扰动，生成"次优布局"作为偏好学习的负样本（**这是获取偏好数据的低成本方法**）
- **顺序增强**：同一块板生成多条不同摆放顺序的专家轨迹

### 3.5 数据版本管理

```
dataset/
  raw/            原始 .brd 归档（只读）
  pdm/v1.2/       中间表示，版本化
  graphs/v1.2/    图数据集
  splits/         训练/验证/测试划分（按项目划分，不能按板随机划分！）
  modules/v1.0/   模块库
  preferences/    专家偏好标注数据
```

**划分原则**：训练/测试集必须**按项目或产品线划分**，不能随机划分。同一项目的不同版本板极其相似，随机划分会造成严重的数据泄漏，评测结果虚高。

## 四、标注工作规划（SME 投入的核心）

| 标注任务 | 预估工作量 | 负责角色 | 时间窗口 |
|---|---|---|---|
| 规范文档 L1/L2/L3 分类复核 | 1000~3000 条 × 1 分钟 ≈ 20~50 人时 | PCB 专家 | 第 1~2 月 |
| 规则 DSL 确认与测试用例 | 200 条 × 15 分钟 ≈ 50 人时 | PCB 专家 + 算法 | 第 2~4 月 |
| 知识库问答评测集 | 300 题 × 10 分钟 ≈ 50 人时 | PCB 专家 | 第 2~3 月 |
| 设计质量分级 | 抽样 200 块 × 5 分钟 ≈ 17 人时 | 资深工程师 | 第 2 月 |
| 模块划分与命名校验 | 抽样 500 模块 × 3 分钟 ≈ 25 人时 | PCB 专家 | 第 3 月 |
| **布局偏好 pairwise 标注** | **3000~5000 对 × 30 秒 ≈ 25~42 人时** | **资深工程师** | 第 4~5 月 |
| 布局结果主观评分 | 100 方案 × 5 分钟 ≈ 8 人时 | 资深工程师 | 第 5~6 月 |
| **合计** | **约 200~250 人时（约 1.5 人月）** | | |

**结论**：标注总量约 200~250 人时，主要集中在规范分类复核和布局偏好 pairwise 标注两块，**需要提前排期**，否则会卡住规则验证和模仿学习的训练节奏。

**标注工具**：建议自研轻量 Web 标注台（pairwise 布局比较界面尤其需要，要能并排渲染两个布局方案并支持缩放）。不要让工程师用 Excel 标注，效率和质量都会崩。

## 五、评测体系

### 五.1 知识库问答评测

**评测集构建**：
- 300+ 题，由 SME 出题，覆盖：数值查询（40%）、原理解释（20%）、多条款综合（20%）、边界/易混淆（10%）、无答案题（10%，考察拒答能力）
- 每题标注：标准答案、必须命中的源文档与章节、难度等级

**评测指标**：

| 维度 | 指标 | 目标 |
|---|---|---|
| 检索 | Recall@5 / Recall@10 | ≥ 92% / ≥ 97% |
| 检索 | MRR、NDCG@5 | 持续跟踪 |
| 生成 | 答案正确率（人工评判） | ≥ 85% |
| 生成 | 数值准确率（数值型问题） | **≥ 98%（数值错了比不答更糟）** |
| 生成 | 引用溯源正确率 | ≥ 95% |
| 生成 | 编造率（Hallucination） | < 2% |
| 生成 | 拒答准确率（无答案题正确拒答） | ≥ 90% |
| 自动化 | RAGAS（faithfulness / answer relevancy / context precision） | 用于日常回归 |

**评测节奏**：每次索引/模型/prompt 变更后跑自动化评测；每月跑一次人工评测。

### 五.2 规则引擎评测

**评测集**：人工构造缺陷板（在正常板上注入已知违规）+ 历史真实问题板

| 指标 | 定义 | 目标 |
|---|---|---|
| 召回率 | 注入缺陷被检出的比例 | ≥ 90% |
| 误报率 | 报出但实际不违规的比例 | < 10% |
| 单规则准确率 | 每条规则单独统计 | 低于 80% 的规则下线整改 |
| 性能 | 1000 器件板全量检查耗时 | < 60s |

**误报率控制**：误报是规则引擎的头号杀手。工程师看到几次误报就再也不用了。建议：
- 新规则先以"提示"级别灰度上线，观察 2 周误报情况再升级为"警告/错误"
- 提供便捷的"这是误报"反馈按钮，进入规则整改队列

### 五.3 辅助布局评测

**评测协议**：

```
测试集：20~30 块 A 级历史板（模型训练时未见过，且来自未见过的项目）
方式：
  1. 遮蔽人类布局，只给模型网表 + 板框 + 固定器件 + 约束
  2. 模型生成布局建议
  3. 三方对比：模型布局 vs 人类布局 vs 商业工具自动布局（若有）
  4. 客观指标计算 + 专家盲评（不告诉评审哪个是 AI 做的）
```

| 指标类别 | 指标 | PoC 目标 |
|---|---|---|
| 合法性 | 硬约束违反数 | **= 0（一票否决项）** |
| 线长 | HPWL / 人类 HPWL | ≤ 1.15 |
| 线长 | 关键网络加权 HPWL 比 | ≤ 1.10 |
| 拥塞 | 拥塞峰值比 | ≤ 1.20 |
| 规范 | 软规则违反数比 | ≤ 1.0（不劣于人类） |
| 人类对齐 | 分区 IoU | ≥ 0.6 |
| 人类对齐 | 关键器件位置偏差（匈牙利匹配后中位数） | ≤ 板对角线的 10% |
| 布通性 | 抽样跑自动布线的布通率 | ≥ 人类布局的 90% |
| **主观** | **专家盲评分（1~5）** | **≥ 3.5** |
| **业务** | **工程师采纳率** | **≥ 40%（关键器件）/ ≥ 50%（外围器件）** |

**采纳率的定义要提前约定清楚**：建议定义为"工程师在最终设计中，该器件位置与 AI 建议位置的距离 < 阈值（如 5mm）"的比例，可自动统计，避免主观争议。

### 五.4 端到端业务指标（PoC 验收）

| 指标 | 测量方式 | 目标 |
|---|---|---|
| 规范查询用时 | 对比实验：10 位工程师，各查 10 个问题，有/无系统 | 降低 ≥ 50% |
| 布局阶段工时 | 3 个试点项目，与历史同类项目对比 | 降低 ≥ 15%（PoC 阶段保守目标） |
| 评审发现的规范问题数 | 试点项目 vs 历史平均 | 降低 ≥ 30% |
| 新人上手周期 | 主观问卷 | 有改善 |
| 系统周活跃用户 | 埋点 | ≥ 20 人 |
| NPS（净推荐值） | 问卷 | > 0 |

## 六、数据安全与合规

| 措施 | 说明 |
|---|---|
| 分级管控 | 所有数据打密级标签，检索时在**向量库/全文库层面**做权限过滤（不能在生成后过滤，会有信息泄漏风险） |
| 训练脱敏 | 项目名、敏感名称、涉密器件型号做一致性映射；映射表加密存储，仅少数人可访问 |
| 受限数据隔离 | 若某些设计有保密限制，需明确是否可用于训练；建议默认排除，逐个申请 |
| 模型防泄漏 | 模型可能记忆训练数据。定期做记忆化测试（用训练集中的特有信息构造探测问题） |
| 审计留痕 | 所有数据访问、导出、训练任务留痕 |
| 数据出境 | 全流程内网，无出口，模型与依赖走离线仓库 |

## 七、数据工程的关键里程碑与验收

| 里程碑 | 时间 | 验收标准 |
|---|---|---|
| D1 数据盘点完成 | 第 2 周 | 清单表格填满，风险项识别 |
| D2 `.brd` 提取管道跑通 | **第 4 周** | **10 块板端到端提取成功，字段完整率 ≥ 95%** |
| D3 文档解析管道跑通 | 第 6 周 | 50 份规范解析入库，表格准确率 ≥ 90% |
| D4 全量文档入库 | 第 10 周 | 全部规范可检索 |
| D5 全量设计提取 | 第 12 周 | ≥ 80% 历史板成功转为 PDM |
| D6 图数据集 v1 | 第 14 周 | 可训练的图数据集，含质量分级 |
| D7 模块库 v1 | 第 16 周 | ≥ 2 万个模块入库并可检索 |
| D8 偏好标注完成 | 第 20 周 | ≥ 3000 对 |

> **D2 是全项目最关键的单点风险**。如果第 4 周还没跑通 `.brd` 批量提取，必须立即启动备用方案（IPC-2581 导出路径），并同步调整布局模块的排期预期。
