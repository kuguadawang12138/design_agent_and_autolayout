## 一、现实约束

| 项 | 现状 |
|---|---|
| 周期 | 6 个月 |
| 算力 | 多卡 GPU（A100/H100/4090） |
| 数据管道 | `.brd` 批量提取尚未验证（**关键路径**） |
| SKILL / EDA 集成 | 提取与写回脚本需要尽早验证 |
| 设计数据授权 | 待确认（**布局线的生死开关**） |
| PCB 领域专家参与 | 待确认 |

**核心矛盾**：完整形态的工作量远超 6 个月能做完的范围。所以本计划的主线是**取舍**，不是压缩。

---

## 二、取舍原则

1. **知识库必须交付**（这是首期最想落地的能力，也是唯一 3 个月内能见效的东西）。
2. **RL 布局必须启动且做深一个点**（这是最终目标，晚启动就来不及）。
3. **规则引擎降级**（它的完整形态需要大量 SME 工时和后端工作量，本期只做地基）。
4. **Allegro 插件降级**（先用文件交换 + 独立客户端）。
5. **凡是"锦上添花"的一律砍掉**：知识图谱、多方案生成、豁免流程、CM 双向同步、多模态图片理解（降到 P2）。

## 四、布局主线（RL/GNN）的风险提示

布局主线最大的风险是**时间被数据工程吃掉**。请务必：

1. **数据管道第 1 个月就要和算法并行开跑**，这是能否做成的前提。
2. **不要追求完美的数据管道**。先用 100 个样本把算法链路跑通，再扩大数据规模。很多人卡在"数据还没准备好"上，半年过去一行模型代码没写。
3. **第 1 个月就把基线做出来**。基线是判断一切的标尺，没有基线的模型效果是没有意义的数字。
4. **M3 的 BC 模型是分水岭**。如果 BC 效果好，说明数据和建模对了，后面 RL 只是锦上添花；如果 BC 效果差，别急着上 RL，回去查数据和特征。
5. **和 SI 仿真建立固定的沟通节奏**（比如每两周一次）。奖励函数写得对不对，只有懂 SI/PI 的人能判断。

## 六、最容易犯的三个错误

1. **只做技术，不建立与设计工程师的连接**。设计工程师是用户、标注者、评审者，也是最终决定方案能否落地的人。**从第一个月就要让几位资深工程师"觉得这是他们的项目"。**
2. **同时开三条战线**。知识库 + 规则引擎 + 布局同时铺开，结果是三个半成品。**必须按本计划严格排序。**
3. **在 RL 上过早投入而忽略基线**。想做 RL 的心情可以理解，但没有基线对比的 RL 结果无法说服任何人，也无法说服自己。**基线先行是对 RL 最好的保护**——只有打赢了基线，RL 的价值才成立。

---

## 七、如果进度进一步吃紧（最小可行版本）

万一数据管道进度不及预期，那就只做两件事：

1. **知识库问答**（6 个月做扎实，准确率 ≥ 85%）
2. **布局数据资产建设 + BC 模型**（6 个月，不做 RL，只做到行为克隆能给出可用建议）

把 RL 放到 V1。**这不丢人**——数据管道、图建模、评估器这些底座建好了，RL 在 V1 阶段只需要 3 个月就能出成果，而基础没打好的 RL 做一年也出不来。
