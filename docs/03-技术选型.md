# 技术选型说明

版本 v0.1 ｜ 约束条件：**纯内网私有化、可离线部署、优先开源可控**

> 说明：具体模型版本迭代很快，选型时请以立项当时的实测评测结果为准。本文给出的是**选型标准与候选集**，以及"为什么这么选"的判断依据。

---

## 1. 选型总原则

1. **能私有化的才进候选**：任何需要外网 API 的商业服务直接排除。
2. **优先中文能力强的开源模型**：规范文档是中文为主，中英混排（术语大量为英文）。
3. **可控 > 先进**：宁可选社区活跃、文档完善、能自己改的方案。
4. **先用成熟组件搭出闭环，再针对瓶颈做定制**：不要一上来就自研全栈。
5. **算法侧唯一例外**：辅助布局没有现成方案可用，必须自研，这里投入定制成本是值得的。

## 2. 大模型与推理

### 2.1 基座 LLM

| 用途 | 候选 | 规模建议 | 说明 |
|---|---|---|---|
| 主对话 / 生成 | **Qwen 系列**（通义千问）、**DeepSeek 系列**、GLM 系列 | 32B~72B（或 MoE 等效） | 中文能力与工具调用是核心考量；需实测中英混排技术文档理解 |
| 抽取 / 分类 / 改写 | 同系列小模型 | 7B~14B | 高吞吐场景（规则抽取、意图分类、查询改写），成本敏感 |
| 多模态（图片理解） | **Qwen-VL 系列**、InternVL 系列 | 7B~32B | 用于规范中的示意图理解、扫描件辅助 |
| 领域微调 | 基于上述基座做 LoRA / QLoRA | — | 用设计规范问答对做轻量微调，**但先把 RAG 做好，微调是后手** |

**重要判断**：**不要一开始就想着微调大模型**。PCB 规范问答的准确率瓶颈 90% 在**检索质量和文档解析质量**，不在生成模型。先把 RAG 打磨到位，再考虑微调。

### 2.2 Embedding 与 Reranker

| 用途 | 候选 | 关注点 |
|---|---|---|
| Embedding | **BGE-M3**、**Qwen3-Embedding**、GTE 系列 | 中英混合、长文本、支持稠密+稀疏混合向量（BGE-M3 的多向量特性对术语匹配很有用） |
| Reranker | **BGE-Reranker-v2-m3**、**Qwen3-Reranker** | Cross-encoder 精排，对提升 Top-5 准确率作用极大，必须要有 |

**领域适配建议**：用设计规范构造正负样本对 Embedding 做对比学习微调（LoRA 即可），通常能带来 5~15 个点的召回提升，性价比远高于微调 LLM。

### 2.3 推理框架

| 选型 | 用途 |
|---|---|
| **vLLM** | 主力推理服务，PagedAttention，高并发首选 |
| **SGLang** | 复杂结构化生成、多轮 Agent 场景可作为备选 |
| **TensorRT-LLM** | 若需极致延迟优化，后期考虑 |
| **Text Embeddings Inference (TEI)** | Embedding / Reranker 专用高性能服务 |

## 3. 知识库（RAG）技术栈

| 环节 | 候选方案 | 选型建议与理由 |
|---|---|---|
| **文档解析** | **MinerU**、Marker、Unstructured、PP-StructureV2、Docling | **建议 MinerU 为主 + 多引擎融合**。PDF 解析质量直接决定天花板，务必在选型阶段用真实规范文档做对比测试，不要看跑分 |
| **OCR** | **PaddleOCR**、Surya、RapidOCR | 中文场景 PaddleOCR 成熟度高 |
| **表格识别** | PP-Structure Table、TableMaster、**LLM 视觉辅助校正** | 规范数值大量在表格中，建议"结构识别 + 多模态模型二次校验"双保险 |
| **公式** | UniMERNet / pix2tex | 优先级低 |
| **分块** | LangChain / LlamaIndex 的层级分块 + 自研规范专用切分器 | 规范文档层级性极强（章-节-条），自研切分器收益大 |
| **向量库** | **Milvus**（大规模、分布式）/ **Qdrant**（轻量、易运维） | 文档量 < 100 万块选 Qdrant，更大或需多租户隔离选 Milvus |
| **全文检索** | **OpenSearch** / Elasticsearch | 必须要有，用于型号、条款号、精确术语的关键词召回 |
| **混合检索融合** | RRF（Reciprocal Rank Fusion） | 简单有效，先用它 |
| **RAG 框架** | **LlamaIndex** / LangChain / Dify / RAGFlow | 建议**自研编排 + 复用组件库**。开箱即用平台（Dify/RAGFlow）适合快速验证，但深度定制（权限过滤、引用校验、规则引擎路由）会受限。**PoC 前 1 个月可用 RAGFlow 快速验证效果，正式版自研** |
| **知识图谱** | **Neo4j** + 自研抽取流程；可参考 GraphRAG 思路 | P2 优先级，先不做。规范条款间的引用关系用关系库也能表达 |
| **评测** | **RAGAS**、TruLens + **自建人工评测集** | **自建评测集是必需品**，至少 300 题，由 SME 出题并给标准答案 |

## 4. 规则引擎技术栈

| 方案 | 优点 | 缺点 | 建议 |
|---|---|---|---|
| **自研 Python DSL**（YAML 定义 + 表达式求值） | 完全可控、与几何计算库无缝集成、易于生成 fix_hint | 需自己做编译器与优化 | **推荐**。PCB 规则大量涉及几何计算（距离、包围盒、区域包含），通用规则引擎在这方面反而累赘 |
| **Drools**（Java） | 成熟、Rete 算法高效 | Java 栈、与 Python 算法栈割裂、几何计算需自己扩展 | 不推荐（技术栈割裂） |
| **Datalog / Souffle** | 声明式、推理能力强 | 学习曲线陡、几何计算不友好 | 可用于规则冲突检测这一子问题 |
| **Z3 / OR-Tools** | 约束求解，可做"给定约束求可行布局" | 规模受限 | **用在布局引擎的合法化阶段**，不用于规则检查 |

**表达式求值**：可用 `asteval` / `simpleeval` 做安全沙箱，或自研 AST 解释器。**不要用 `eval()`**。

**几何计算库**：
- **Shapely**：2D 几何（多边形、距离、相交、缓冲区），PCB 场景主力
- **NumPy / SciPy**：批量向量化计算，`scipy.spatial.cKDTree` 做最近邻查询（找最近电源引脚这类高频操作）
- **Rtree / STRtree**：空间索引，1000+ 器件的规则检查性能关键

**规则抽取（LLM 辅助）**：
- 用结构化输出（JSON Schema 约束生成 / Outlines / Guidance）保证抽取结果可解析
- 抽取 → 人工确认 → 单元测试（每条规则配 1 个正例 + 1 个负例设计片段）→ 上线

## 5. 辅助布局技术栈（核心自研）

### 5.1 图学习

| 组件 | 选型 | 理由 |
|---|---|---|
| 图框架 | **PyTorch Geometric (PyG)** | 生态最好、异构图支持完善（`HeteroData`、`to_hetero`）、算子丰富 |
| 备选 | DGL | 大规模分布式训练更强，但社区活跃度近年不如 PyG |
| 模型 | **异构图 Transformer（HGT）** / **GraphSAGE** / **GAT** / **GINE**（含边特征） | PCB 图是天然异构图（器件节点、引脚节点、网络节点），HGT 类模型更贴合 |
| 超边处理 | Net 作为独立节点（星形展开）或超图卷积 | **推荐 Net 作为节点**，避免大 Net（如 GND 上千引脚）clique 展开导致边爆炸 |
| 位置编码 | 拉普拉斯特征向量 / 随机游走位置编码 | 让 GNN 感知全局结构 |

### 5.2 强化学习

| 组件 | 选型 | 理由 |
|---|---|---|
| RL 框架 | **Ray RLlib** / **CleanRL** / Stable-Baselines3 | RLlib 适合大规模分布式采样；CleanRL 单文件实现便于深度魔改（**布局问题必然要魔改，推荐 CleanRL 风格自研**） |
| 算法 | **PPO**（主力）、**IMPALA**（大规模采样）、**离线 RL：CQL / IQL / Decision Transformer** | **先做模仿学习（BC）与离线 RL，再上 PPO 微调** |
| 环境 | 自研 `gymnasium` 接口的 PCB 布局环境 | 必须自研；性能是关键，评估函数需向量化/GPU 化 |
| 并行采样 | Ray / EnvPool 风格向量化环境 | RL 采样效率决定训练周期 |
| 动作掩码 | 自研 mask 生成器（复用规则引擎） | 保证硬约束绝不违反 |

### 5.3 优化与合法化

| 用途 | 选型 |
|---|---|
| 解析式布局精细优化 | 参考 **DREAMPlace** 思路（把布局写成可微目标，用 GPU 梯度下降优化），自研 PyTorch 实现 |
| 力导向初始化 | 自研（简单有效，用于给 RL 提供初始解） |
| 模拟退火 / 局部搜索 | 自研，用于后处理微调 |
| 合法化（消重叠、对齐网格） | 自研 + **OR-Tools CP-SAT**（小规模精确求解） |
| 相似子图匹配 | 图嵌入近似检索（向量库）+ **NetworkX / VF2** 精确验证 |
| 拥塞估计 | 自研网格化 RUDY / 快速全局布线 |

### 5.4 训练基础设施

| 组件 | 选型 |
|---|---|
| 深度学习框架 | PyTorch 2.x |
| 分布式训练 | PyTorch DDP / FSDP；RL 采样用 Ray |
| 实验管理 | **MLflow**（私有化友好）或 Weights & Biases 私有部署 |
| 数据版本 | **DVC** 或 LakeFS |
| 超参搜索 | Optuna / Ray Tune |
| 可视化 | TensorBoard + 自研布局渲染（matplotlib / SVG） |

## 6. EDA 集成技术栈

| 组件 | 技术 | 说明 |
|---|---|---|
| Allegro 插件 | **SKILL**（Cadence 专有 Lisp 方言） | 菜单、面板、板数据读写、图形高亮 |
| 本地代理 | **Python**（打包为 exe，PyInstaller）或 C++ | 负责 HTTP 通信、缓存、大文件传输；SKILL 通过 `ipcBeginProcess` / 文件/socket 与之通信 |
| 批量数据提取 | **Allegro Extracta** + 自研视图文件 + Python 解析器 | 批处理历史 `.brd` |
| 无界面批处理 | `allegro -s`（Server 模式）+ SKILL 脚本 | 用于自动化提取与写回 |
| 中立格式 | **IPC-2581 XML 解析器**（自研或社区库） | 兜底与跨 EDA |
| 约束数据 | Constraint Manager 导出（CSV/XML）+ 解析器 | 规则对齐 |
| 3D / 结构 | STEP / IDX 解析（`pythonocc` / `cadquery`） | 限高与结构约束，P1 |

> **需在项目第一周验证的技术点**：
> 1. Allegro 版本是否支持 `allegro -s` 无界面批处理（不同版本/License 类型差异大）
> 2. SKILL 能否发起网络请求，或必须走本地代理
> 3. Extracta 能导出哪些字段，是否包含 Room、Keepout、限高等布局关键信息
> 4. 是否有 Allegro X 系列的新 API（部分新版本提供了更现代的接口）

## 7. 平台与工程技术栈

| 层 | 选型 |
|---|---|

## 8. 技术风险与验证优先级

| 优先级 | 待验证技术点 | 验证方式 | 失败后备方案 |
|---|---|---|---|
| **P0** | Allegro `.brd` 批量结构化提取 | 拿 10 块历史板跑 Extracta，检查字段完整性 | 转 IPC-2581 导出路径 |
| **P0** | 规范 PDF 表格解析准确率 | 拿 20 份真实规范跑多引擎对比 | 关键表格人工结构化录入 |
| **P0** | SKILL 与外部服务通信 | 写一个最小 Demo：Allegro 内点按钮，调用外部接口返回结果 | 文件交换 + 轮询 |
| **P1** | 500~5000 板的数据质量与可用比例 | 抽样 50 块板做质量评估 | 缩小训练集，加重检索复用路线 |
| **P1** | 布局环境的采样吞吐 | 实测每秒可完成多少次布局评估 | GPU 化评估函数 / 降低问题规模 |
| **P2** | GNN 在 5000 节点图上的训练效率 | 基准测试 | 子图采样 / 分层建模 |

## 9. 需要慎重的几个"看起来很美"的选项

| 选项 | 为什么要慎重 |
|---|---|
| 一上来就微调大模型 | RAG 的瓶颈在检索与解析，微调是最后一步，不是第一步 |
| GraphRAG 全量建图 | 成本高、收益在规范问答场景不明显；先做好混合检索 |
| 纯端到端 RL 做全板布局 | 6 个月内做不出来，且工程师不会接受黑盒全自动结果 |
| 直接复用芯片布局的开源实现 | PCB 与 IC 的问题结构差异大（见术语表第三章），需大量改造，参考思想而非代码 |
| 开箱即用的 RAG 平台做最终产品 | 权限过滤、引用校验、规则路由、EDA 集成都需要深度定制 |
| 一步到位上 K8s + 全套云原生 | 若运维能力有限，会拖慢 PoC；先 Docker Compose 跑通，V1 再上 K8s |
